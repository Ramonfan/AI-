# 第 5 课：iOS 用 Moya / Alamofire 解析结构化结果

本课目标：让 iOS 明确承接后端返回的结构化 JSON，并把网络请求迁移到 Moya / Alamofire。

---

## 1. 这一课在整个 AI App 里的位置

```text
OpenAI Structured Outputs
→ 后端 Pydantic SummarizeResponse
→ HTTP JSON
→ iOS Codable NoteSummary
→ SwiftUI SummaryResultView
```

这条链路的核心是：每一层都知道自己期望的结构。

你要重点形成一个判断：

```text
AI App 不是让 iOS 直接相信模型文本。
更稳的做法是：模型先按 schema 输出，后端用 Pydantic 校验，iOS 再用 Codable 解码。
```

## 3. 后端返回什么

后端成功响应：

```json
{
  "title": "结构化输出",
  "summary": "本课学习用 JSON Schema 约束模型输出。",
  "keywords": ["Structured Outputs", "JSON Schema", "Pydantic"],
  "todos": ["验证后端", "检查 iOS 解析"]
}
```

后端失败响应：

```json
{
  "detail": "note 不能为空"
}
```

---

## 4. iOS 用什么接

成功响应用：

```swift
struct NoteSummary: Codable, Equatable {
    var title: String
    var summary: String
    var keywords: [String]
    var todos: [String]
}
```

失败响应用：

```swift
private struct BackendErrorResponse: Decodable {
    let detail: String
}
```

学习重点：

```text
Codable 不只是“方便解析 JSON”。
它是 iOS 侧对后端 JSON 契约的声明。
```

## 5. Moya / Alamofire 在这里怎么分工

本项目当前依赖版本：

```text
Moya：15.0.3
Alamofire：5.12.0
```

在这套写法里，你可以这样理解：

```text
Moya：声明“我要请求哪个接口，以及请求怎么组装”
Alamofire：真正执行底层 HTTP 请求
BackendConfiguration：统一决定后端 baseURL
RemoteSummaryService：把 Moya 的回调结果转成 async/await，并处理业务解码
SummaryViewModel：只关心 SummaryService，不关心具体网络框架
```

所以 ViewModel 没有直接 import Moya，这是刻意保留的边界。

---

## 6. MiniAINotesAPI 做了什么

`MiniAINotesAPI` 遵守 `TargetType`，用一个 enum 描述接口：

```swift
enum MiniAINotesAPI {
    case summarize(note: String)
}
```

它把一个接口拆成几个固定部分：

```text
baseURL：从 BackendConfiguration 读取后端服务地址
path：接口路径，比如 /api/summarize
method：请求方法，比如 POST
task：请求体如何编码，比如 requestJSONEncodable
headers：请求头，比如 Content-Type: application/json
sampleData：Moya stub 测试时用的样例数据
```

这一层适合放“接口描述”，不适合写 UI 状态，也不适合处理页面错误文案。

后端地址为什么单独抽出来：

```text
模拟器访问 Mac：127.0.0.1
真机访问 Mac：Mac 的局域网 IP
后续设置页修改地址：写入 UserDefaults
```

如果这些逻辑都写在 `MiniAINotesAPI` 里，Moya Target 会慢慢变成“接口 + 环境配置 + 调试逻辑”的混合体，不利于学习和维护。

## 7. RemoteSummaryService 做了什么

`RemoteSummaryService` 的职责是网络层，不负责 UI。

它做四件事：

```text
1. 把 note 编码成 JSON 请求体
2. 用 MoyaProvider 发 POST 请求，底层由 Alamofire 执行
3. 2xx 时解码 NoteSummary
4. 非 2xx 时解码 detail 并抛出中文错误
```

网络层分成两块：

```text
MiniAINotesAPI：描述接口路径、method、task、headers
RemoteSummaryService：发起请求、处理状态码、解码成功和失败响应
```

ViewModel 仍然只依赖 `SummaryService` 协议，不直接知道 Moya 或 Alamofire。

---

## 8. 为什么错误也要结构化

如果只显示状态码：

```text
后端请求失败，状态码：422
```

用户不知道哪里错了。

如果解析后端 `detail`：

```text
后端请求失败：note 不能为空
```

这对调试和产品体验都更好。

---

## 9. 为什么要写 Moya stub 测试

如果每次验证网络解析都必须启动后端，学习效率会很低。

这次测试用了 Moya 的 stub 能力，直接模拟三类响应：

```text
1. 200 + 完整 JSON：应该解码成 NoteSummary
2. 422 + {"detail": "..."}：应该显示后端错误 detail
3. 200 + 结构不完整 JSON：应该显示可读解码错误
```

这说明我们验证的是 iOS 网络层自己的责任：拿到 HTTP 响应之后，能不能稳定处理。

# 第 10 课：财报分析 RAG 上下文

## 这一课做什么

这一课先做 RAG v0：不急着引入向量数据库和 Embedding，而是在后端放一组本地财报阅读知识片段，用关键词检索把相关片段附加到财报分析结果里。

核心流程是：

```text
iOS 输入公司名
-> 后端 Provider 获取结构化财报事实
-> 本地 Retriever 根据指标、摘要、风险和追问检索知识片段
-> 后端把 Provider 事实 + retrieved_contexts 交给 AI 或规则解读
-> iOS 展示财报结果和“参考知识”
```

## RAG 的两条主干

理解 RAG 不能只记一个词，要把它拆成两条链路：

```text
资料准备链路：文档 -> chunk -> embedding -> vector store
用户提问链路：question -> embedding -> retrieve -> prompt -> answer
```

第一条是离线建设，解决“知识怎么被系统保存成可检索形态”。

第二条是在线推理，解决“用户提问时怎么找到相关知识，并让模型基于这些知识回答”。

### 主干一：资料准备链路

```text
文档
-> 切片 chunk
-> 向量化 embedding
-> 写入 vector store
```

每一步的作用：

- 文档：原始知识来源，可以是 PDF、网页、Markdown、公告、财报、课程笔记。
- chunk：把长文档切成小片段，因为模型和检索系统都不适合直接处理整本资料。
- embedding：把每个 chunk 转成向量，向量表达的是“语义位置”，不是关键词本身。
- vector store：保存 chunk、向量和元数据，方便后续按相似度查找。

### 资料准备链路中的节点职责

| 节点 | 接收什么 | 它做什么 | 输出什么 | 为什么需要它 |
|---|---|---|---|---|
| document | 原始资料 | 提供知识来源 | 一篇或多篇长文本 | 没有文档，RAG 没有外部知识来源 |
| chunk | 长文档 | 按段落、标题、长度或语义边界切成小片段 | 多个可检索文本块 | 长文档太大，不能直接全部塞进 Prompt，也不利于精确检索 |
| embedding | 单个 chunk | 用 embedding 模型把文本转换成向量 | 一组数字向量 | 向量能表达语义相似度，让系统找到“意思相近”的内容 |
| vector store | chunk、embedding、来源元数据 | 存储向量并支持相似度搜索 | 可查询的知识索引 | 用户提问时可以快速找到相关 chunk |

这一段要特别记住：

```text
chunk 负责把知识切小；
embedding 负责把文字变成可比较的语义坐标；
vector store 负责把这些语义坐标存起来，并支持检索。
```

这条链路的输入是资料，输出是可检索知识库。

如果没有这条链路，RAG 就没有“可被检索的知识”。模型只能靠自己已有参数回答，容易不知道最新资料、私有资料或项目内部规则。

### 主干二：用户提问链路

```text
question
-> question embedding
-> retrieve
-> prompt
-> answer
```

每一步的作用：

- question：用户提出的问题。
- question embedding：把问题也转成向量，和知识库里的 chunk 向量放到同一个语义空间比较。
- retrieve：从 vector store 找出和问题最相关的 topK chunks。
- prompt：把用户问题和检索到的上下文一起交给模型。
- answer：模型基于上下文生成答案，最好同时返回引用来源。

### 用户提问链路中的节点职责

| 节点 | 接收什么 | 它做什么 | 输出什么 | 为什么需要它 |
|---|---|---|---|---|
| question | 用户问题 | 表达用户当前想知道什么 | 一段查询文本 | 这是在线链路的入口 |
| question embedding | 用户问题 | 把问题转换成向量 | 问题向量 | 让问题能和 chunk 向量做相似度比较 |
| retrieve | 问题向量、vector store | 找出最相关的 topK chunks | retrieved_context | 把可能有用的知识从库里取出来 |
| prompt | question、retrieved_context、业务规则 | 组织模型输入 | 完整模型上下文 | 告诉模型必须基于哪些资料回答 |
| answer | prompt | 模型生成回答 | 答案和引用 | 最终返回给用户的结果 |

这一段要特别记住：

```text
retrieve 不是回答问题；
retrieve 只是找资料；
answer 才是模型基于资料生成回答。
```

这条链路的输入是用户问题，输出是带上下文依据的回答。

如果没有这条链路，即使知识库已经建好，模型也拿不到相关资料；知识只是躺在库里，不会进入回答过程。

## RAG 的概率视角

不用 RAG 时，可以理解为：

```text
P(answer | question)
```

模型只根据问题和自身参数生成答案。

使用 RAG 时，可以理解为：

```text
P(answer | question + retrieved_context)
```

模型不是凭空回答，而是在“问题 + 检索上下文”的条件下生成答案。

所以 RAG 的核心价值不是让模型变聪明，而是改变模型回答时的条件：把私有知识、最新资料、业务规则放进上下文里。

## 为什么先做关键词 RAG

RAG 的关键不是一上来就用向量库，而是先把“检索上下文进入业务链路”这件事跑通。

这一课故意只用 Python 标准库做三件事：

- 维护一组可解释的本地知识片段。
- 根据财报分析结果拼出检索 query。
- 返回 top 3 片段，并带上 `source_id`、`title`、`text`、`score`。

这样调试时能直接看到：为什么命中这条知识、分数来自哪里、AI 或规则层拿到了什么上下文。

## 后端新增内容

新增 `app/rag_service.py`：

```text
FinancialReportAnalysisResponse
-> build_financial_report_context_query
-> retrieve_contexts_for_query
-> attach_retrieved_contexts
```

知识库目前覆盖：

- 收入增长拆解
- 毛利率与成本压力
- 经营现金流和利润质量
- 资产负债表韧性
- 风险与业务驱动因素
- 管理层指引

普通接口 `/api/financial-report/analyze` 和流式接口 `/api/financial-report/analyze/stream` 都会在 Provider 成功后附加 `retrieved_contexts`。

## AI 和规则层怎么用上下文

非流式 AI 解读和流式 AI 解读都会通过 `build_financial_report_narrative_input` 收到：

```text
retrieved_contexts: [...]
```

没有 OpenAI Key 或模型不可用时，规则降级文本也会显示“参考知识”，所以不消耗额度也能验证 RAG 链路。

## iOS 新增内容

iOS 新增：

```swift
FinancialReportContextSnippet
FinancialReportAnalysis.retrievedContexts
```

`retrieved_contexts` 使用 `decodeIfPresent`，旧后端不返回该字段时会默认解码为空数组。

结果页在存在上下文时显示“参考知识”区块，每条展示标题、正文和检索分数。

## 这课要掌握的点

- Provider 事实和 RAG 知识不是一回事：前者回答“这家公司发生了什么”，后者提供“怎么阅读这些事实”的解释框架。
- RAG 结果要可见，否则很难判断模型是否真的基于上下文工作。
- 先用关键词检索跑通接口契约，再升级 Embedding / 向量数据库，学习路径更稳。
- RAG 必须分清资料准备链路和用户提问链路：前者建知识库，后者用知识库回答问题。

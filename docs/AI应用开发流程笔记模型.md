# AI 应用开发流程笔记模型

这份模型用于约束后续所有学习笔记。以后每学习一个新技能，不只记录“它是什么”，更要记录“它在 AI 应用开发流程中处在哪一环、为什么需要它、输入输出是什么、失败时怎么办”。

---

## 0. 笔记质量标准

每篇落地笔记必须能把当前环节讲透。合格笔记不只是记录名词和代码，而是要回答完整的“为什么、是什么、怎么流转、失败怎么办、怎么验证”。

一篇合格笔记至少要讲清：

- 知识：这个环节涉及哪些核心概念。
- 原理：这些概念为什么成立，背后机制是什么。
- 逻辑：请求、数据、状态、错误在这一环如何流动。
- 边界：这个环节负责什么，不负责什么。
- 依赖：它依赖哪些上游输入，又给下游提供什么。
- 失败：它常见失败点是什么，系统怎么降级或恢复。
- 落地：它在当前项目里的代码、接口、数据模型分别在哪里。
- 验证：怎么证明它真的跑通，而不是只写了代码。

如果一篇笔记只能回答“我改了哪些文件”，但不能回答“这个环节为什么这样设计”，就不算完成。

---

## 1. 笔记整理目标

每篇笔记都要服务于复习和迁移。

复习指的是：

```text
以后回看时，能快速想起这个技能解决了什么问题。
```

迁移指的是：

```text
以后做新的 AI App 时，知道这个技能应该放在哪一层、和谁交互、如何验证。
```

所以笔记不要写成流水账：

```text
今天写了 A 文件，又改了 B 文件，然后跑了 C 命令。
```

而要写成流程模型：

```text
这个技能属于 AI 应用链路的哪一环？
它接收什么输入？
它产出什么输出？
它依赖前一环什么条件？
它失败会影响后一环什么状态？
```

---

## 2. AI 应用开发总流程

后续所有笔记都优先映射到这条链路上：

```text
业务目标
-> 用户输入
-> 客户端状态
-> 网络请求
-> 后端接口
-> 数据 Provider
-> 数据契约
-> AI 编排
-> 模型调用
-> 结果返回
-> 客户端展示
-> 错误处理
-> 观测与验证
```

当前财报分析项目可以具体化为：

```text
输入公司名
-> iOS ViewModel 进入 loading / streaming
-> Moya / Alamofire 请求 FastAPI
-> 后端识别市场
-> SEC / A 股 Provider 获取财报事实
-> Pydantic 统一响应模型
-> Prompt 拼接事实和上下文
-> OpenAI Responses API 生成分析
-> JSON 或 SSE 返回
-> iOS Codable 解码
-> SwiftUI 展示结果
-> 失败时保留 partial 或 fallback
```

## 5. 每类技能的笔记重点

不同技能不要用同一种写法。要按它在系统里的职责写。

### iOS 技能

重点写：

- 用户操作如何变成状态变化。
- ViewModel 如何承接 loading / success / failure / partial。
- Service 如何隔离网络细节。
- Codable 如何保护数据解析边界。
- UI 如何展示业务结果，而不是暴露底层错误。

典型问题：

```text
这个状态从哪里来？
什么时候变化？
失败时用户还能看到什么？
```

### 后端技能

重点写：

- 路由接收什么请求。
- Service 层做什么业务编排。
- Provider 从哪里拿数据。
- Pydantic 如何约束响应。
- 错误如何转换成可读结果。

典型问题：

```text
这个接口到底是在转发、编排、校验，还是降级？
```

### AI 应用技能

重点写：

- 模型拿到的输入是什么。
- 哪些事实来自业务系统，哪些内容允许模型生成。
- Prompt 如何约束模型行为。
- Structured Outputs 如何让结果可解析。
- RAG 如何把外部上下文注入模型。

典型问题：

```text
模型是在补充表达，还是在决定事实？
```

### 工程化技能

重点写：

- 为什么先写 OpenSpec。
- 为什么先 Mock。
- 这一步如何验证。
- 哪些失败路径被覆盖。
- 这次改动会不会破坏前后端契约。

典型问题：

```text
我怎么证明这个流程真的跑通了？
```

## 7. 示例：SSE 流式服务应该怎么记

不要只记：

```text
SSE 是 Server-Sent Events，后端用 StreamingResponse，iOS 用 streamRequest。
```

应该这样记：

```text
所属环节：
结果返回 -> 客户端展示 -> 错误处理

解决的问题：
AI 生成时间长，一次性等待体验差，所以把完整结果拆成连续事件。

输入：
后端已经拿到的 Provider 事实，以及 AI 生成过程中的文本片段。

输出：
status / provider_result / delta / done。

失败路径：
Provider 前失败是 failure；Provider 后 AI 中断是 partial；收到 done 才是 success。

项目落点：
FastAPI StreamingResponse + iOS Alamofire streamRequest + SSE parser。
```

这样以后复习时，你会记住它在系统里的位置，而不是只记住 API 名字。

## 8. 示例：RAG 应该怎么记

不要只记：

```text
RAG = Retrieval-Augmented Generation。
```

应该这样记：

```text
所属环节：
数据 Provider -> 数据契约 -> AI 编排

解决的问题：
模型缺少私有知识、最新知识和业务解释框架，直接回答容易幻觉。

概率视角：
不用 RAG：P(answer | question)
使用 RAG：P(answer | question + retrieved_context)

两条主干：
资料准备：文档 -> chunk -> embedding -> vector store
用户提问：question -> embedding -> retrieve -> prompt -> answer

资料准备链路：
文档是原始知识；chunk 把长文档拆成可检索片段；embedding 把片段转成语义向量；vector store 保存向量、原文和来源元数据。

用户提问链路：
question 先转成 embedding；retrieve 用问题向量找最相关的 chunks；prompt 把问题和 retrieved_context 放在一起；answer 是模型基于上下文生成的回答。

输入：
用户问题、Provider 事实、可检索知识库。

输出：
topK 相关上下文，进入 Prompt，并在客户端展示引用。

失败路径：
检索为空时不阻断主流程；模型不可用时规则层仍可展示参考知识。

验证方式：
能看到命中的 chunk、分数、来源；能证明这些上下文进入了 prompt；客户端能展示引用。
```

这样以后学向量库、Embedding、Rerank 时，都能放回 RAG 这条主线里。

RAG 类笔记必须明确区分：

- 离线资料准备链路：知识如何进入系统。
- 在线用户提问链路：知识如何参与回答。
- 检索结果可观测性：为什么命中、命中了什么、有没有进入 Prompt。
